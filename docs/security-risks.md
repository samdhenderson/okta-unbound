# Security: residual risks & verification

_The findings register for Okta Unbound: what a reviewer should scrutinize, what was
fixed, what is accepted and why — plus the commands and tests that let a reviewer
reproduce the claims without trusting the prose. The posture itself (trust model, threat
model, and the controls that enforce it) lives in [`security.md`](./security.md)._

**Status:** point-in-time, re-verified against source on **2026-09-09**; symbols are cited
by name (line numbers drift).

---

## 1. Residual risks & known gaps

This assessment is deliberately not marketing-clean — it is what a reviewer should
scrutinize. The findings below were surfaced by reading the code. Findings 1–8 were
remediated on 2026-07-20; **each fix was re-checked against current source on 2026-09-09**
and still holds — the `Status` column says what was re-verified and how, so a "Fixed"
here is a claim about today's code, not a historical note. Findings 9–12 are accepted
rather than fixed: 9 is a platform property, 10 is the deliberate cost of an undo that can
actually restore, 11 is unread payload behind a deliberate leniency, and 12 is the stated
limit of a pattern-based redactor.

## 2. How to verify independently

A reviewer can reproduce the core claims without trusting this document:

- **No external message surface:** `grep -rn "externally_connectable\|onMessageExternal" src manifest.json` → only comments/absence.
- **No dynamic execution / HTML injection:** `grep -rn "eval(\|new Function\|dangerouslySetInnerHTML\|innerHTML\|document.write" src` → production hits are zero (matches are tests/JSDoc).
- **No secrets:** `grep -rn "SSWS \|Bearer \|Authorization" src` → zero hits.
- **XSRF never stored/logged:** read `getXsrfToken` in [`content/apiRequest.ts`](../src/content/apiRequest.ts); run the regression test in [`content/index.test.ts`](../src/content/index.test.ts) ("never passes the XSRF token or a request/response body to the logger").
- **Only five response headers leave the page context:** read `FORWARDED_RESPONSE_HEADERS` / `collectForwardedHeaders` in [`content/apiRequest.ts`](../src/content/apiRequest.ts); the "forwarded response headers" cases in [`content/apiRequest.test.ts`](../src/content/apiRequest.test.ts) assert the rest of the bag is dropped.
- **`scripting` has exactly one call site:** `grep -rn "chrome.scripting" src` → only [`background/reinjectContentScripts.ts`](../src/background/reinjectContentScripts.ts), whose targets come from `chrome.runtime.getManifest()`.
- **No credentials or tokens at rest:** `grep -rn "storage\.\(local\|sync\|session\)\.set" src` → cache payloads, UI state, audit/undo/request-log history, and one integer rate-limit threshold; nothing session-bearing.
- **No credential key can be written or captured:** read `assertNoExcludedKeys` in [`useOktaApi/profileOperations.ts`](../src/sidepanel/hooks/useOktaApi/profileOperations.ts) and the caps in [`shared/undoManager.ts`](../src/shared/undoManager.ts) (`MAX_CAPTURED_ATTRIBUTES`, `MAX_CAPTURED_VALUE_CHARS`); both are covered by unit tests.
- **Quality gates:** every PR runs lint (0 errors), strict type-check, the coverage
  gate (thresholds in [`vitest.config.ts`](../vitest.config.ts)), and the Storybook build/story tests
  ([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)).

The security-hardening rules these controls enforce are codified as house rules in
[`CLAUDE.md`](../CLAUDE.md); the rationale for each individual control is carried in the
module header of the file that implements it.

## 3. Reporting a vulnerability

Please report suspected vulnerabilities privately via a
[GitHub security advisory](https://github.com/samdhenderson/okta-unbound/security/advisories/new)
rather than a public issue, or through the contact in [`../PRIVACY.md`](../PRIVACY.md).
Include reproduction steps and affected version; please allow reasonable time for a fix
before public disclosure.
